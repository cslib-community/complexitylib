# Parameterized computation and kernelization

Parameterized complexity keeps encoded input length and an instance parameter separate. The parameter is an arbitrary map `κ : α → Nat`; a language is a set of typed instances with an injective encoding `enc : α ↪ List Bool`. The native machine reads only `enc a`. Declaring a parameter does not give it a separate register or an oracle for the parameter's value. The models here are native deterministic resource contracts and polynomial-time preprocessing interfaces. [complexitylib][complexitylib]

## One algorithm, potentially ineffective bounds

Write `L = |enc a|` and `k = κ a`. [`FPT`](https://github.com/cslib-community/complexitylib/blob/13e6a31951bf1c89a1a6258c44f9444aecbbefd8/Complexity/Computability/Complexity/Parameterized.lean#L123) requires bound witnesses and then one native decision procedure valid for every input, with time bounded up to a global affine constant by `f(k) (L+1)^c`. The exponent `c` is independent of the parameter. [`XP`](https://github.com/cslib-community/complexitylib/blob/13e6a31951bf1c89a1a6258c44f9444aecbbefd8/Complexity/Computability/Complexity/Parameterized.lean#L131) permits `f(k) (L+1)^g(k)`, so the degree can vary with the slice. Both use [`DecidableInTimeO`](https://github.com/cslib-community/complexitylib/blob/13e6a31951bf1c89a1a6258c44f9444aecbbefd8/Complexity/Computability/Complexity/FineGrained.lean#L96), whose workspace bound is independently existential; neither imposes a separate small-space requirement.

The quantifiers do not require `κ`, `f`, or `g` to be computable. This is a uniform algorithm with possibly ineffective parameter bounds, not a separately chosen algorithm for each slice. It differs from Definitions 1.2–1.3 of Cygan et al., which require computable bound functions and present instances as `(x,k)` with size `|x|+k`. The library's encoding can instead encode a numerical parameter in binary. [cygan2015][cygan2015]

The finite-sum argument in [`mem_FPT_iff_exists_monotone`](https://github.com/cslib-community/complexitylib/blob/13e6a31951bf1c89a1a6258c44f9444aecbbefd8/Complexity/Computability/Complexity/Parameterized.lean#L203) replaces an arbitrary bound by a monotone majorant; it does not establish computability. Likewise, [reparameterization](https://github.com/cslib-community/complexitylib/blob/13e6a31951bf1c89a1a6258c44f9444aecbbefd8/Complexity/Computability/Complexity/Parameterized.lean#L186) requires only `κ(a) ≤ h(κ'(a))`, without an effectiveness condition on `h`. The module proves `P ⊆ FPT ⊆ XP` and identifies both [FPT](https://github.com/cslib-community/complexitylib/blob/13e6a31951bf1c89a1a6258c44f9444aecbbefd8/Complexity/Computability/Complexity/Parameterized.lean#L448) and [XP](https://github.com/cslib-community/complexitylib/blob/13e6a31951bf1c89a1a6258c44f9444aecbbefd8/Complexity/Computability/Complexity/Parameterized.lean#L458) with `P` when the parameter is globally bounded.

## Functions and parameter-respecting reductions

[`ComputableInFPTTime`](https://github.com/cslib-community/complexitylib/blob/13e6a31951bf1c89a1a6258c44f9444aecbbefd8/Complexity/Computability/Complexity/Parameterized.lean#L247) asks for a total native computation of `f : α → β` with both time and visited-work-cell space bounded by `F(κ(a)) (L+1)^c`. This common bound is not an independent space restriction on the FPT class: [the native time-to-FPT bridge](https://github.com/cslib-community/complexitylib/blob/13e6a31951bf1c89a1a6258c44f9444aecbbefd8/Complexity/Computability/Complexity/Parameterized.lean#L281) absorbs the fixed machine's work-tape count into `F`, since each step visits only a bounded number of new cells. Output is uncharged to raw workspace, but emitting it costs time. [`mem_FPT_iff_computableInFPTTime`](https://github.com/cslib-community/complexitylib/blob/13e6a31951bf1c89a1a6258c44f9444aecbbefd8/Complexity/Computability/Complexity/Parameterized.lean#L408) characterizes FPT membership by a Boolean decider satisfying this function predicate.

[`FPTReducible`](https://github.com/cslib-community/complexitylib/blob/13e6a31951bf1c89a1a6258c44f9444aecbbefd8/Complexity/Computability/Complexity/Parameterized.lean#L537) adds membership preservation and a target-parameter bound `κB(f(a)) ≤ h(κA(a))`. The reducing function has a native FPT computation; its time multiplier and `h` remain arbitrary. [`ComputableInFPTWithParam`](https://github.com/cslib-community/complexitylib/blob/13e6a31951bf1c89a1a6258c44f9444aecbbefd8/Complexity/Computability/Complexity/Parameterized.lean#L528) exposes the computation and parameter conditions separately for the generic many-one calculus. The relation is transitive and pulls back both [FPT](https://github.com/cslib-community/complexitylib/blob/13e6a31951bf1c89a1a6258c44f9444aecbbefd8/Complexity/Computability/Complexity/Parameterized.lean#L581) and [XP](https://github.com/cslib-community/complexitylib/blob/13e6a31951bf1c89a1a6258c44f9444aecbbefd8/Complexity/Computability/Complexity/Parameterized.lean#L588). Composition uses finite majorants rather than an unrecorded monotonicity assumption. Other bounded reduction interfaces are described in [Reductions and information access](reductions.md).

## Kernels and the decidability boundary

[`IsKernelization`](https://github.com/cslib-community/complexitylib/blob/13e6a31951bf1c89a1a6258c44f9444aecbbefd8/Complexity/Computability/Complexity/Parameterized/Kernelization.lean#L88) packages `K : α → α` and `g : Nat → Nat` with four obligations:

| Obligation | Formal content |
|---|---|
| Efficient preprocessing | `K` is native polynomial time in the original encoded input length. |
| Same decision problem | `K(a) ∈ A ↔ a ∈ A`. |
| Small encoded output | `encodedLength(K(a)) ≤ g(κ(a))`. |
| Controlled output parameter | `κ(K(a)) ≤ g(κ(a))`. |

The output stays in the same instance type and language. [`HasKernel`](https://github.com/cslib-community/complexitylib/blob/13e6a31951bf1c89a1a6258c44f9444aecbbefd8/Complexity/Computability/Complexity/Parameterized/Kernelization.lean#L100) existentially quantifies `K` and arbitrary `g`; [`HasPolyKernel`](https://github.com/cslib-community/complexitylib/blob/13e6a31951bf1c89a1a6258c44f9444aecbbefd8/Complexity/Computability/Complexity/Parameterized/Kernelization.lean#L105) additionally requires `g` to be polynomially bounded. The latter supplies a polynomial majorant, without declaring the original witness `g` computable. Separate bounds on length and parameter differ by at most a factor two from a bound on their sum. Cygan et al.'s Definition 2.1 requires a computable size bound; `HasKernel` omits that requirement. [cygan2015][cygan2015]

[`mem_FPT_iff_hasKernel`](https://github.com/cslib-community/complexitylib/blob/13e6a31951bf1c89a1a6258c44f9444aecbbefd8/Complexity/Computability/Complexity/Parameterized/Kernelization.lean#L278) assumes a nonempty instance type and an existing native decision bound `A ∈ DTIME enc t`, for some length-based function `t`. Under those hypotheses, `A ∈ FPT enc κ ↔ HasKernel enc κ A`. The reverse implication runs the kernel and then the supplied decider. Having a small equivalent instance alone does not assert decidability.

The forward construction [`hasKernel_of_mem_FPT`](https://github.com/cslib-community/complexitylib/blob/13e6a31951bf1c89a1a6258c44f9444aecbbefd8/Complexity/Computability/Complexity/Parameterized/Kernelization.lean#L181) performs a polynomially bounded universal simulation of the FPT decider. If it halts, preprocessing outputs a fixed yes- or no-instance with the matching answer; otherwise it returns the original instance, whose size is then bounded in terms of the parameter. It need not compute `f(k)` or `κ(a)`. This implements the timeout argument of the standard FPT-to-kernel proof; compare Cygan et al., Lemma 2.2, retaining the effectiveness difference above. [`hasPolyKernel_of_mem_P`](https://github.com/cslib-community/complexitylib/blob/13e6a31951bf1c89a1a6258c44f9444aecbbefd8/Complexity/Computability/Complexity/Parameterized/Kernelization.lean#L290) separately gives a polynomial kernel for every `P` language over a nonempty type. These results do not make every FPT kernel polynomial.

## SAT and the exact-cardinality vertex-cover client

[`SAT_mem_FPT`](https://github.com/cslib-community/complexitylib/blob/13e6a31951bf1c89a1a6258c44f9444aecbbefd8/Complexity/Computability/Complexity/Parameterized.lean#L229) places CNF satisfiability in FPT for the number of distinct variables; the module also covers each fixed clause-width restriction. The more detailed client is [`VertexCover_mem_FPT`](https://github.com/cslib-community/complexitylib/blob/13e6a31951bf1c89a1a6258c44f9444aecbbefd8/Complexity/Computability/Complexity/Parameterized/VertexCover.lean#L396), with the native bound in [`VertexCover_decidableInExpTime_one`](https://github.com/cslib-community/complexitylib/blob/13e6a31951bf1c89a1a6258c44f9444aecbbefd8/Complexity/Computability/Complexity/Parameterized/VertexCover.lean#L365) corresponding to `2^k` times a polynomial in encoded input length.

The target problem has a material convention: [`VertexCover`](https://github.com/cslib-community/complexitylib/blob/13e6a31951bf1c89a1a6258c44f9444aecbbefd8/Complexity/Computability/Complexity/Problems/VertexCover.lean#L86) asks for a cover of **exactly** `k` vertices from the declared vertex set. It is equivalent to an at-most-`k` cover only when `k` does not exceed the number of distinct declared vertices, as stated in [`mem_VertexCover_iff_exists_card_le`](https://github.com/cslib-community/complexitylib/blob/13e6a31951bf1c89a1a6258c44f9444aecbbefd8/Complexity/Computability/Complexity/Problems/VertexCover.lean#L110). A triangle with `k=4` is therefore rejected. The search procedure caps its internal unary search depth by the vertex count and checks that the cap equals the binary target. A huge binary target does not force a correspondingly huge polynomial-time preprocessing loop.

The explicit [`bussKernel`](https://github.com/cslib-community/complexitylib/blob/13e6a31951bf1c89a1a6258c44f9444aecbbefd8/Complexity/Computability/Complexity/Parameterized/VertexCover/BussKernel.lean#L454) uses high-degree vertices forced into every small cover, then densely relabels the remaining active vertices. It retains enough isolated vertices to pad a cover to the exact target size. This differs from the at-most-`k` presentation in Cygan et al., Section 2.2.1, where isolated vertices can be discarded. [cygan2015][cygan2015]

The source proves these bounds for every input, including rejected inputs:

| Output quantity | Bound in the original target `k` | Declaration |
|---|---|---|
| Listed vertices | `k(k+2)` | [`length_bussKernel_vertices_le`](https://github.com/cslib-community/complexitylib/blob/13e6a31951bf1c89a1a6258c44f9444aecbbefd8/Complexity/Computability/Complexity/Parameterized/VertexCover/BussKernel.lean#L573) |
| Listed edges | `(k(k+1))^2` | [`length_bussKernel_edges_le`](https://github.com/cslib-community/complexitylib/blob/13e6a31951bf1c89a1a6258c44f9444aecbbefd8/Complexity/Computability/Complexity/Parameterized/VertexCover/BussKernel.lean#L581) |
| Encoded instance length | `40(k+1)^6` | [`length_encode_bussKernel_le`](https://github.com/cslib-community/complexitylib/blob/13e6a31951bf1c89a1a6258c44f9444aecbbefd8/Complexity/Computability/Complexity/Parameterized/VertexCover/BussKernel.lean#L589) |
| Output target | `max(k,1)` | [`bussKernel_snd_le`](https://github.com/cslib-community/complexitylib/blob/13e6a31951bf1c89a1a6258c44f9444aecbbefd8/Complexity/Computability/Complexity/Parameterized/VertexCover/BussKernel.lean#L610) |

The fixed rejection instance is an empty graph with target one, explaining the `max(k,1)` allowance. [`computableInPolyTime_bussKernel`](https://github.com/cslib-community/complexitylib/blob/13e6a31951bf1c89a1a6258c44f9444aecbbefd8/Complexity/Computability/Complexity/Parameterized/VertexCover/BussKernel.lean#L601) proves native polynomial-time preprocessing under `encPair encGraph encNat`; [`isKernelization_bussKernel`](https://github.com/cslib-community/complexitylib/blob/13e6a31951bf1c89a1a6258c44f9444aecbbefd8/Complexity/Computability/Complexity/Parameterized/VertexCover/BussKernel.lean#L618) packages its contract, and [`VertexCover_hasPolyKernel`](https://github.com/cslib-community/complexitylib/blob/13e6a31951bf1c89a1a6258c44f9444aecbbefd8/Complexity/Computability/Complexity/Parameterized/VertexCover/BussKernel.lean#L635) concludes a polynomial kernel. These are the actual encoded-size bounds; a smaller literature kernel is not substituted for them.

## Color coding and fpt-reductions between graph problems

[`LongPath`](../../Complexity/Computability/Complexity/Problems/LongPath.lean) is k-Path: a graph with a duplicate-free list of `k` declared vertices whose consecutive entries are adjacent. For `k+1` vertices this is a Mathlib `SimpleGraph.Walk.IsPath` of length `k` on the induced graph (`mem_LongPath_succ_iff`). The target `k = 0` is accepted by the empty path.

[`ColorfulPath`](../../Complexity/Computability/Complexity/Parameterized/ColorCoding.lean) is the colored problem solved by the dynamic programming of Alon, Yuster and Zwick. An instance is a graph, a list of colors parallel to the vertex list (the color of a vertex is the entry at its first occurrence, `0` when the list is short), and a target `k`. The question is whether some path on `k` vertices has pairwise distinct colors, all less than `k`. Color sets are bit masks. `ColorCoding.mem_table_getD` proves that the table entry at a mask lists exactly the endpoints of colorful paths with that color set. `colorfulPathBool_eq_true_iff` proves the decider correct. [alonyusterzwick1995][alonyusterzwick1995] [cygan2015][cygan2015]

The resource statement is coarser than the RAM analysis. The table on `N` masks is polynomial-time with `N` in unary (`ColorCoding.computableInPolyTime_table`). The decider pads the instance by `2^min(n,k)`, where `n` is the number of distinct vertices. The parameter `k` is written in binary, so padding by `2^k` itself could be exponential in the input length. Capping at `n` keeps the padding below `2^n`, and the decider rejects `k > n` outright. [`DecidableInExpTime.of_computableInPolyTime_pad`](../../Complexity/Computability/Complexity/FineGrained/Padding.lean) assumes three things. First, a Boolean procedure `Ψ` is polynomial-time on `encPair enc encUnary`. Second, an exponent `ν` is polynomial-time computable into unary with `ν ≤ μ`. Third, `a ∈ A ↔ Ψ (a, 2^ν a) = true`. Under these it gives a native machine within time `2^(δμ)` times a polynomial in the encoded length, for an existential `δ`. Hence `ColorfulPath_decidableInExpTime` and `ColorfulPath_mem_FPT`. The `2^k` operation count of the source is not claimed for multi-tape machines.

The randomized algorithm for k-Path, which colors uniformly at random and repeats, is not yet formalized; see issue #2870.

[`fptReducible_Clique_IndependentSet`](../../Complexity/Computability/Complexity/Parameterized/Clique.lean) and its converse complement the graph on its declared vertices and keep `k`. This polynomial-time map is an `FPTReducible` instance, so `Clique` and `IndependentSet` are together in `FPT` (`Clique_mem_FPT_iff`) and in `XP`.

## The W-hierarchy

The *weft* of a circuit ([`Circuit.weft`](../../Complexity/Computability/Circuit/Weft.lean)) is its depth with costs in which a gate of more than two arguments costs one and every other gate costs nothing. So it is the largest number of large gates on a path to the output. [`WeightedCircuitSAT`](../../Complexity/Computability/Complexity/Parameterized/WHierarchy.lean) asks whether a one-output circuit over the unbounded fan-in basis (negation, and conjunction and disjunction of any arity) has a satisfying input with exactly `k` ones. `WCS t d` restricts it to circuits of weft at most `t` and depth at most `d`. Its instances are typed: a circuit packaged with proofs of the two bounds (`WeftCircuit t d`), encoded as the circuit alone, plus the weight in binary. A reduction to `WCS t d` must therefore produce circuits that provably lie in the class. The cited definition likewise restricts instances to circuits of the class. `W t enc κ` is the class of problems that fpt-reduce to `WCS t d` for some `d`, with the weight as parameter. [cygan2015][cygan2015]

The module proves that `W t` is closed under fpt-reductions (`FPTReducible.mem_W`), increasing in `t` (`W_mono`), and contains `FPT` (`FPT_subset_W`): an fpt decider selects the fixed instance `WCS.yesInstance` or `WCS.noInstance` of `WCS t 1`. Fan-in is counted as arity with multiplicity, and the basis has constants and unary gates; neither changes the classes, since merging repeated arguments only lowers weft and constants propagate. `WHard t` is hardness under fpt-reductions; `wHard_iff` reduces it to every `WCS t d`, and `WHard.subset_FPT` says that a `W[t]`-hard problem in `FPT` puts `W[t]` in `FPT`.

[`IndependentSet_mem_W`](../../Complexity/Computability/Complexity/Parameterized/WHierarchy/IndependentSet.lean) builds, in polynomial time, a circuit with one input per distinct declared vertex. It negates every input, takes for every edge between distinct declared vertices the disjunction of the negations of its ends, and outputs the conjunction of these disjunctions. A satisfying input of weight `k` is an independent set of `k` declared vertices (`toCircuit_satisfiableWithWeight_iff`). The final conjunction is the only large gate, so the circuit has weft at most `1` and depth at most `3`. These bounds use the reusable method in [`Circuit/Encoding/Layer.lean`](../../Complexity/Computability/Circuit/Encoding/Layer.lean) for circuits built as codes. `evalCode_layer` evaluates a block of gates that reads only earlier wires. `le_of_mem_evalCode_depth_layer` adds the largest cost in the block to the depth bound, and `Circuit.depthWith_le_of_evalCode` turns the result into a weft or depth bound for the circuit. Edges with an undeclared end and self-loops are dropped, matching `Graph.toSimpleGraph` restricted to declared vertices. `Clique_mem_W` follows through the complement reduction. The converse, W[1]-hardness of `Clique` (an fpt-reduction from every `WCS 1 d`), is not yet formalized; see issue #2966. Theorem numbers in Cygan et al. Chapter 13 have not been checked against the book; the declarations cite Section 13.3.

## OR-distillation and `coNP ⊆ NP/poly`

Kernelization lower bounds rest on the theorem of Fortnow and Santhanam: no `NP`-hard problem has a weak OR-distillation unless `coNP ⊆ NP/poly`. The library proves this implication. It does not assume `coNP ⊄ NP/poly`. [bodlaenderjansenkratsch2014][bodlaenderjansenkratsch2014] [fortnowsanthanam2011][fortnowsanthanam2011]

[`NPPoly enc`](../../Complexity/Computability/Complexity/Classes/NP/Advice.lean) is `NP` with polynomial advice. An advice function `adv : ℕ → List Bool` with polynomially bounded length is paired with a problem `B ∈ NP (encPair encBits enc)`, and `a ∈ A ↔ (adv |enc a|, a) ∈ B`. The advice depends only on the encoded length, and the verifier of `B` reads it as part of its input. `coNPPoly` is the class of complements. `NP` lies in `NPPoly`, and both classes are closed downward under polynomial-time many-one reductions (`PolyTimeReducible.mem_NPPoly`). `coNP_subset_NPPoly_iff` states that `coNP ⊆ NP/poly ↔ NP ⊆ coNP/poly`, and `coNP_subset_NPPoly_of_coNPComplete` derives the inclusion from a single `coNP`-complete member. Yap's collapse of the polynomial hierarchy to its third level is not formalized.

[`IsORDistillation encA encB A B f s`](../../Complexity/Computability/Complexity/Parameterized/Distillation.lean) is Definition 4 of Bodlaender, Jansen and Kratsch. It has three obligations:

| Obligation | Formal content |
|---|---|
| Efficient | `f : List α → β` is native polynomial time on `encList encA`. |
| OR property | `f l ∈ B ↔ ∃ a ∈ l, a ∈ A`, for every nonempty list `l`. |
| Short output | If `l` is nonempty and every entry has encoded length at most `n`, then `|encB (f l)| ≤ s n`. |

The output bound is independent of the number of entries. The value on the empty list is unconstrained, since Definition 4 concerns `t ≥ 1` instances. The size bound `s` is not required to be computable. Time is polynomial in the encoded list length, `t + 2(|x₁| + ⋯ + |xₜ|)` for `t` entries. The source bounds time by a polynomial in `∑ |xᵢ|`, which implies the library bound, so the library's time hypothesis is weaker. The two agree when no instance has an empty encoding.

`coNP_subset_NPPoly_of_orDistillation` and `NP_subset_coNPPoly_of_orDistillation` are the `NP ⊆ coNP/poly` conclusion of Theorem 2 of the source, for any `NP`-hard problem in place of `SAT`, any target problem `B`, and a polynomially bounded size bound. The conclusion holds for every instance encoding. Theorem 2 also concludes `PH = Σ₃`, through Yap's theorem; that collapse is not formalized. The theorem number in the Fortnow–Santhanam paper itself was not verified; the cited locator is the one in Bodlaender, Jansen and Kratsch.

The proof is stated in the class-wise form needed for cross-composition. [`IsPolyEquivalence enc r`](../../Complexity/Computability/Complexity/Parameterized/Distillation.lean) is Definition 8 of the source: `r` is an equivalence relation decidable in polynomial time, and the instances up to length `n` meet at most `c n` classes, for a polynomially bounded `c`. `compl_mem_NPPoly_of_orCompression` makes three assumptions. First, `f` is polynomial time with the OR property on nonempty lists of pairwise related instances. Second, `t` is polynomially bounded. Third, every list of exactly `t n` related instances of length exactly `n` maps to an output shorter than `t n`. The conclusion is `Aᶜ ∈ NPPoly enc`. The theorem also takes a `Decoder enc`, since the verifier parses a list of instances from its certificate. `coNP_subset_NPPoly_of_orCompression` removes the decoder for `NP`-hard problems. It transfers the hypotheses along a reduction from `SAT`, whose formulas have a decoder, and pulls the relation back with `IsPolyEquivalence.comap`. In the source this argument appears inside the proof of Theorem 6, the cross-composition theorem. That theorem, polynomial compressions and their kernel corollaries are not formalized here.

The advice is chosen by a counting argument. [`Finset.exists_tupleCover`](../../Complexity/Foundations/Combinatorics/TupleCover.lean) considers a map `F` from `t`-tuples into a set `Y` with `#Y < 2^t`. For every finite `R`, it finds at most `⌊log₂ #R⌋ + 1` values of `F` such that every element of `R` is an entry of a tuple over `R` mapped to one of them. This is the counting behind the Fortnow–Santhanam theorem for compression to fewer than `t` bits. The complementary witness lemma, Lemma 1 of the source, which the source attributes to Dell and van Melkebeek without reproducing its proof, allows compression to `O(t log t)` bits; that case needs a cover by a number of values polynomial in `t` rather than the halving argument, and is not formalized. For each class and each length `n`, the library applies it to the no-instances of length `n` and keeps the resulting compressed words as advice. A verifier then accepts a no-instance `a` when it is given a list of related instances that contains `a` and compresses to an advice word. Every entry of such a list is a no-instance, because the advice word is also the compression of a list of no-instances, and the OR property holds for both lists.

## Checked examples and scope

The inspected [Parameterized tests](https://github.com/cslib-community/complexitylib/blob/13e6a31951bf1c89a1a6258c44f9444aecbbefd8/ComplexityTests/Parameterized.lean#L1) instantiate bounded parameters, restricted-CNF FPT reductions, Boolean closure, and a constant kernel with both yes- and no-instances. They exercise the triangle at targets one through four. The [VertexCoverKernel tests](https://github.com/cslib-community/complexitylib/blob/13e6a31951bf1c89a1a6258c44f9444aecbbefd8/ComplexityTests/VertexCoverKernel.lean#L1) check dense relabeling, isolated-vertex padding, rejection from too many forced or active vertices, and a target exceeding the vertex count. These are existing test sources, not new compilation results. The [ColorCoding tests](../../ComplexityTests/ColorCoding.lean) evaluate the colorful-path decider by `decide` on accepted and rejected colorings of a four-vertex path, including `k = 0`, colors at least `k`, and `k` above the vertex count. The [WHierarchy tests](../../ComplexityTests/WHierarchy.lean) evaluate weft and depth of small circuits by `decide`. They check weighted satisfiability of a three-input conjunction at weights `3` and `2`, and use the circuit of the triangle to show that it has an independent set of one vertex and none of two. They also check that edges with an undeclared end and self-loops are ignored. The [Distillation tests](../../ComplexityTests/Distillation.lean) show that the distillation hypotheses are satisfiable. "Some entry is `true`" is an OR-distillation of `{true}` with output length one, which places `{false}` in `NPPoly encBool`. Equal length is a polynomial equivalence relation on bit strings with `n + 1` classes up to length `n`, and the class-wise theorem with `t n = 2` places the all-`false` strings in `NPPoly encBits`. The tests also check a concrete halving cover and `SAT ∈ NPPoly encCNF`.

The survey compared the displayed quantifiers and quantitative bounds with the pinned source fragments linked above. This was a textual check, not Lean elaboration or an audit of the proofs.

The local library declarations discussed here have candidate upstream markers. The [model map](../model-map.md) indexes the explanatory pages; declaration links here identify the pinned locations. This page describes FPT, XP, parameter-respecting reductions, kernels, vertex-cover endpoints, colorful k-Path, the circuit definition of the W-hierarchy with Independent Set and Clique in W[1], and the Fortnow–Santhanam distillation theorem; it does not infer a machine characterization of the W-hierarchy, W[1]-hardness, an effective-bound strengthening, or a kernelization lower bound for a concrete parameterized problem.
