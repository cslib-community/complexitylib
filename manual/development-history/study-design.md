# Study design and remaining evidence

## What is already measurable

The manual reports a fixed source census, first-parent Git chronology, local project-path transcript censuses, role-stratified duration distributions, verified short excerpts, three matched PR intervals, one selected-day merge-group cohort and one exact-revision job timeline. These support descriptive claims with explicit denominators. Generated records are not shipped: source/Git analyses can be rerun from the fixed history; session analysis needs private access or separately retained exports, and mutable GitHub records may no longer reproduce the original observations.

## What remains missing

The requested exhaustive automated-development record is not yet available. Desktop access failed before connection, and local records stop before the source cutoff. Other providers/accounts, deleted sessions, remote workers, resumed conversations, predecessor repositories and direct human edits may also be absent. The absence of a transcript is not evidence that a commit was autonomous or that no human intervention occurred.

The next collection step is read-only inventory of the relevant Codex/Claude stores on `samuel@desktop`, using the same cutoff and preserving original session IDs, parent IDs and content hashes. Copied records should be deduplicated before adding counts. Desktop data may fill gaps or duplicate local stores; its contribution must be measured after the join. Connection credentials and unrelated conversations are not research data.

## Unit of analysis for a paper

A useful task record would join the initial human objective, issue scope, author/worker/reviewer sessions, code revisions, PR proposal, reviews, CI attempts, merge/disposition and later reversions or semantic corrections. The unit must include unsuccessful and abandoned tasks. A merged PR is often only a milestone; the original mathematical objective must remain visible.

For each task, distinguish model selection, mathematical proof design, Lean implementation, resource realization, source-mapping review, API review, integration and presentation. Several agents may contribute to one task and one conversation may span many tasks. Record interventions such as clarifying a model, rejecting a weak substitute, supplying a proof idea, changing an interface, requesting deletion or approving scope. The selected excerpts provide examples of such coding categories, not a completed coding study.

## Measurements that would require further work

| Proposed claim | Evidence needed before making it |
|---|---|
| Fraction of work autonomous | Operational definition, complete task/intervention corpus, independent annotation and uncertainty |
| Time to formalize a theorem | Defined start/end, pre-existing prerequisites, all parallel workers, waiting, failures and recovery |
| Agent/model comparison | Comparable assigned tasks, tool/environment controls, full attempts and consistent telemetry |
| Review effectiveness | Known defects before/after review, reviewer independence, false positives/negatives and source-mapping checks |
| Cache speedup | Matched or randomized runs, correctness-equivalent outputs, setup/download/upload time, misses/failures and resource controls |
| Maintainability improvement | Representative client changes, later repair burden, build effects and reviewer/user assessment |

The existing source and records can motivate these questions but do not answer them causally. No financial cost should be reconstructed from incomplete model labels and token fields without a defined pricing/accounting basis.

## Threats to validity

Selection is conditioned on surviving local stores and integrated repository history. Squashing, rebasing, imported code and shared Git identities obscure attribution. Conversation summaries can repeat earlier events; provider role fields can contain synthetic messages. Concurrent agents create overlapping timing intervals. Clock skew and inconsistent logging conventions can affect joins. Public issues can be edited after the event; saved snapshots record retrieval content, not every historical revision.

The source snapshot itself is unusually large and fast-changing. The review inventories model families and traces selected endpoints, not every proof. Agent reviewers can share blind spots. Novel or surprising endpoints require mathematical scrutiny beyond checking that their Lean dependencies compile. Neither a favorable review nor a negative historical case should be generalized to the whole library without additional evidence.

## Publication preparation

Before submission, freeze the chosen source and supplementary data; establish contributor-approved authorship/source credit; resolve the desktop coverage gap or explicitly bound the study; verify the manuscript's main theorem-to-source mappings; archive the exact public GitHub evidence; and choose a controlled-access arrangement for private transcripts. These are concrete remaining research steps, not claims already completed by this dossier. A library-design paper can still be written with a bounded observational development section if the missing records remain unavailable.
